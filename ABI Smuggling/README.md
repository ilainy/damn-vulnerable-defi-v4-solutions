# ABI Smuggling

## 一、题目简介

典型的**ABI 走私 + 权限绕过**高危合约漏洞场景，核心为带自定义权限校验的通用执行器合约。开发者为金库合约设计了一套自主授权机制，仅允许白名单权限调用指定函数，同时划分了普通提款与紧急清空资金两套逻辑，试图隔离风险操作。

合约核心规则：金库内置 `AuthorizedExecutor`通用执行器，所有外部调用必须通过 `execute` 方法执行目标操作。系统通过自定义算法校验调用权限，仅开放 `withdraw` 普通提款权限给用户，高危清空资金函数 `sweepFunds` 未对普通用户授权，且该函数受`onlyThis` 修饰，仅允许合约自身调用，用于紧急风控兜底。

看似严谨的权限校验逻辑，因**硬编码 calldata 偏移读取、权限校验与实际执行逻辑割裂**，存在致命绕过漏洞，攻击者可无权限提空金库全部资产。

基础环境参数：

- 金库初始资产：**1000000 DVT**

- 可授权普通函数：`withdraw`（限额、限时提款）

- 高危未授权函数：`sweepFunds`（一键清空全部资金）

- 权限校验逻辑：固定 calldata 偏移读取选择器校验权限

解题目标：绕过合约权限校验与函数调用限制，掏空金库内全部 DVT 代币，并将所有资产转入指定 recovery 回收账户。

## 二、审计视角

### 1\. 核心高危漏洞：ABI Smuggling（ABI 走私）权限绕过

合约 `execute` 权限校验逻辑存在根本性设计缺陷，开发者通过汇编硬编码固定偏移量读取函数选择器用于权限校验：固定从整体 calldata 的 **100 字节偏移位置**读取4字节选择器，以此判断操作是否授权。但实际执行逻辑会按照**标准 ABI 编码规则**解析 calldata 并执行对应函数。

这就造成了**权限校验数据源 ≠ 实际执行数据源**的致命割裂：攻击者可手动构造恶意 calldata，在校验偏移位置放置合法授权函数选择器（`withdraw`）骗过权限检测，在真实执行区域放置高危未授权函数（`sweepFunds`），实现完全权限绕过。  
出问题的源代码:
```solidity
function execute(address target, bytes calldata actionData) external nonReentrant returns (bytes memory) {
    // Read the 4-bytes selector at the beginning of `actionData`
    bytes4 selector;
    uint256 calldataOffset = 4 + 32 * 3; // calldata position where `actionData` begins
    //自以为要读取 actionData 最开头的函数选择器,实际上固定读取整个交易 calldata 的第 100 字节位置（4+32*3=100）
    assembly {
        selector := calldataload(calldataOffset); // 漏洞在这里
    }

    if (!permissions[getActionId(selector, msg.sender, target)]) {
        revert NotAllowed();
    }

    _beforeFunctionCall(target, actionData);

    return target.functionCall(actionData); // 实际执行这里
}
```

### 2\. 自调用防护机制失效

高危清空函数 `sweepFunds` 配置 `onlyThis` 修饰器，要求仅合约自身可调用。但 `execute`内部通过 `target.functionCall(actionData)` 发起内部调用，调用者上下文会被切换为合约自身，天然满足 `onlyThis` 调用条件，二层防护机制完全失效。

### 3\. 业务风控缺失严重

合约权限体系仅依赖单层自定义选择器校验，无任何兜底防护：无调用身份二次校验、无函数黑白名单硬限制、无calldata合法性校验、无高危操作拦截机制。通用执行器模式搭配错误的偏移校验逻辑，直接导致全部权限体系崩塌。

## 三、开发者默认安全假设

1\. **硬编码偏移安全迷信**：错误认为固定 calldata 偏移读取选择器的校验方式，能够匹配真实函数执行逻辑，忽略ABI动态编码的灵活性。

2\. **权限隔离认知错误**：认为通过自定义权限映射+白名单机制，可严格隔离普通操作与高危操作，未考虑权限绕过场景。

3\. **修饰器过度信任**：盲目依赖 `onlyThis` 修饰器防护高危函数，未预判通用执行器内部调用可绕过外部身份限制。

4\. **单级风控依赖**：将全部安全寄托于单层选择器权限校验，未搭配函数签名二次核验、调用行为风控等多层机制。

## 四、同类项目审计点

1\. **禁止硬编码 calldata 偏移**：所有权限校验、函数鉴权逻辑，禁止使用汇编固定偏移读取 calldata 数据，极易引发 ABI 走私漏洞。

2\. **校验与执行数据源统一**：权限校验使用的函数选择器、调用参数，必须与实际执行的 calldata 数据完全一致，杜绝数据割裂。

3\. **通用执行器重点审计**：所有包含 `execute`、通用代理调用、自定义调用转发的合约，是权限绕过、ABI走私漏洞的高发区，必须重点核验。

4\. **区分内外调用风控**：`onlyThis`、内部调用场景需单独做风控加固，不可单纯依赖修饰器做安全防护。

5\. **高危函数硬隔离**：资金清空、权限修改等高危函数，需做硬编码拦截，禁止通过通用执行器调用，不依赖动态权限表。

## 五、完整解题思路

1\. **梳理校验偏移规则**：确认合约权限校验固定读取 calldata 100字节位置的选择器，以此作为绕过突破口。

2\. **构造双层恶意 calldata**：手动拼接完整调用数据，在100字节校验位置填入已授权的 `withdraw` 选择器，骗过权限校验逻辑。

3\. **植入真实恶意逻辑**：在标准ABI执行区域，填入高危 `sweepFunds` 调用数据，配置回收账户与代币参数。

4\. **利用自调用特性**：通过 `execute` 内部调用，让 `sweepFunds` 满足 `onlyThis` 调用条件，绕过身份限制。

5\. **执行攻击完成通关**：直接调用拼接好的恶意 calldata，触发权限绕过，一键清空金库全部 DVT 并转入 recovery 账户。

## 六、报错复盘

### 报错1：WithdrawalWaitingPeriodNotEnded 提款冷却报错

**报错原因**：calldata 构造错误，权限校验位置与执行位置未割裂，合约真实执行了 `withdraw` 普通提款函数，触发15天冷却时间校验失败。

**解决方案**：严格按照ABI动态类型编码规则拼接完整 calldata，保证校验位为合法选择器、执行位为恶意清空函数，实现真正的ABI走私绕过。

### 报错2：NotAllowed 权限校验失败

**报错原因**：手动拼接 calldata 偏移量、填充位、数据长度不规范，100字节位置未精准放置授权选择器，权限校验不通过。

**解决方案**：严格对齐32字节ABI占位规则，精准填充偏移量、零值占位、数据长度，保证校验位置数据合法。

### 报错3：函数未执行、资产未转移

**报错原因**：恶意 `sweepFunds` 参数编码错误、数据长度不匹配，导致函数调用无响应。

**解决方案**：标准化编码目标地址、代币参数，严格匹配函数ABI格式。

## 八、合约修复方案

1\. **统一校验与执行数据源**：删除汇编硬编码固定偏移读取选择器的危险逻辑，基于真实解析后的 calldata 获取函数选择器，保证校验、执行逻辑数据源完全一致。

2\. **高危函数硬隔离**：将 `sweepFunds` 等资金清空高危函数，从通用执行器可调用列表中硬编码拦截，禁止外部通过 `execute` 转发调用。

3\. **增加calldata合法性校验**：对传入的动态 actionData 做格式校验，禁止畸形、错位、拼接类恶意 calldata，封堵ABI走私入口。

4\. **强化自调用风控**：高危函数叠加管理员权限校验、紧急开关校验，仅指定管理员可触发资金清空，不单纯依赖 `onlyThis`修饰器。

5\. **废弃自定义不安全权限体系**：摒弃固定偏移校验的自定义鉴权逻辑，采用成熟的 OpenZeppelin 权限体系，避免自研安全逻辑漏洞。

## 九、漏洞总结

ABI Smuggling 漏洞的核心本质是**合约鉴权逻辑与执行逻辑的数据源不一致**。开发者自研通用执行器与权限校验体系，错误使用硬编码固定偏移读取calldata做权限判断，违背标准ABI编码规则，导致攻击者可通过拼接双层结构的恶意calldata，实现权限完全绕过。



本题同时暴露了两大安全误区：一是盲目自研鉴权、代理转发逻辑，替代成熟安全组件；二是过度依赖修饰器、单层权限校验做风控，缺失多层兜底防护。此类ABI走私、权限绕过漏洞普遍存在于自定义代理、通用执行器、合约转发类业务中，是智能合约审计的核心高危盯点。
